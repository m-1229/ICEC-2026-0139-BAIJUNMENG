## 一、本阶段要解决的实际问题

第四阶段的结论是：`Smoke detector, smoke alarm`（索引 393）和 `Baby cry, infant cry`（索引 20）在现有 12 个文件上分离度很好，候选规则能在 1.92 s 内检出，负样本零触发。

**但这个"零触发"是假的。** 因为现有 12 个文件里，没有任何一段是"日常环境声音"：

| 现有集合 | 文件数 | 时长 | 性质 |
|---|---|---|---|
| 烟雾报警（真报警器） | 2 | 82.51 s | **正样本** |
| 婴儿哭声（真哭声） | 1 | 131.08 s | **正样本** |
| 门铃 / 敲门 / 水壶 | 9 | 125.12 s | **其他目标类别**，不是日常背景 |

需要说准确一点：第四阶段做烟雾报警判定时，负样本集是"其余 10 个文件"，即 **9 段另外三类目标 + 1 段真婴儿哭声**。婴儿哭对烟雾判定而言确实是负样本，但它同样不是"日常背景"。所以：

> 现有集合中，**真正的日常环境负样本数量 = 0**。

而真实家庭里天天出现、且最可能触发误报的东西 —— 微波炉"叮"、手机闹钟、电视、吸尘器、洗衣机 —— **一段都没有**。

这就是本阶段的全部意义：**补的不是数量，是覆盖面的空白**。

## 二、两个必须先讲清的方法学问题

这两点会直接决定这批数据有没有用，所以放在清单前面。

### 2.1 静音文件不算负样本

第三阶段已经证明：工具对整段做判断时，**静音段会把分数摊平**（`敲门.wav` 54% 时长贴近本底噪声，Knock 峰值只有 0.0126）。反过来也成立：

> 一段 30 秒里只有 1 秒有微波炉"叮"、其余 29 秒是安静房间的录音，**几乎必然不触发**。但这不是"模型没误报"，这是"模型没听到东西"。

如果拿这种文件当负样本，会得出一个虚假乐观的结论，然后上线被真实环境打脸。

**因此对每条负样本设硬性要求：**

| 要求 | 下限 | 理由 |
|---|---|---|
| 总时长 | ≥ 10 s（建议 15–30 s） | 至少要覆盖 10 个以上分析窗 |
| 有声活动占比 | ≥ 50% 时长 | 避免静音稀释导致的假阴性 |
| 事件次数 | 2–5 次/段 | 单次短促提示音（如一声"叮"）只有 0.1 s，会被 0.96 s 窗严重稀释 |
| 峰值电平 | −20 ~ −3 dBFS | 太低等于没录到；削波会引入失真（参考 `kettle_whistle` 1995 个满幅样本） |

确认"有声活动占比"，用现有工具即可估算（`yamnet_batch_eval.py` 会输出峰值 dBFS、RMS 与"过短/过静/裁剪"告警），不需要新增依赖。

### 2.2 这批数据只能用来"验伪"，不能用来调阈值

第四阶段的候选阈值是在**同一批 12 个文件**上选出来的。如果现在拿新负样本回头再调阈值，就等于用测试集训练 —— 报出来的数字一定好看，上线一定失效。

**纪律：**

1. 本批负样本只回答一个问题：**"现有的候选规则会不会被日常声音触发？"**（是/否 + 在哪个时间点）
2. **不得**根据本批结果调整 0.45 / 0.50 这类参数
3. 如果确实发现了必须改的问题，**另开第二批独立样本复核**，并在报告里明确标注"参数在 A 批上调整、在 B 批上验证"
4. 报告里不得出现"准确率""误报率"字样，只能写"在 N 段样本中，M 段触发"

## 三、目录结构与命名规范

### 3.1 为什么必须放在 `recordings/` 之外

`yamnet_frame_diagnosis.py` 用 `GROUPS[cat]` 按**父目录名**取类别定义，而 `GROUPS` 只有 5 个键（`门铃/敲门/烟雾报警/水壶/婴儿哭声`）。把负样本放进 `recordings/微波炉/`，脚本会直接 `KeyError` 崩掉。

所以负样本必须放在**同级独立目录**。设计如下（**共 14 个目录 = 2 个分组父目录 + 12 个叶子目录**）：

```
D:\SmartLife\yamnet_prototype\
├─ recordings\                    ← 现有 12 个文件，不动
│  ├─ 门铃\  敲门\  烟雾报警\  水壶\  婴儿哭声\
└─ recordings_negative\           ← 本阶段【不创建】，待你确认后再建
   ├─ A_smoke_confusers\          ① 分组父目录 · 烟雾报警混淆源
   │  ├─ phone_alarm\             ②  手机闹钟
   │  ├─ microwave\               ③  微波炉提示音
   │  ├─ tv_audio\                ④  电视声音
   │  ├─ vacuum\                  ⑤  吸尘器
   │  ├─ washer\                  ⑥  洗衣机
   │  └─ other_beeps\             ⑦  其他电子提示音
   ├─ B_cry_confusers\            ⑧ 分组父目录 · 婴儿哭声混淆源
   │  ├─ speech\                  ⑨  普通谈话
   │  ├─ pet\                     ⑩  宠物叫声
   │  ├─ tv_voice\                ⑪  电视中的人声
   │  └─ cry_like\                ⑫  其他类似哭声的声音
   ├─ C_semantic\                 ⑬ 电视/媒体里播放的报警声或婴儿哭声（见 8.2）
   └─ unknown\                    ⑭ 无法确认真实类别
```

> **本阶段不创建以上任何目录。** 你已明确"暂时不建"，本节仅作结构设计；真正落地时按此一次建齐，避免中途改路径导致 `metadata.csv` 里的相对路径作废。

### 3.2 命名规范

```
{group}_{source}_{index}.wav

示例：
phone_alarm_pixel6_01.wav
microwave_midea_02.wav
tv_audio_livingroom_03.wav
vacuum_dyson_01.wav
speech_family_04.wav
pet_cat_neighbor_02.wav
```

- **全小写、纯 ASCII、下划线分隔**。理由：中文文件名在 PowerShell 控制台会显示成乱码（前几轮已反复遇到，`门铃.wav` 被打成 `闂ㄩ搦.wav`），评估时得靠读 JSON 才能确认是哪个文件，平白增加出错概率。
- `source` 写设备/来源的短标识，用于满足"不同设备来源"这一要求
- `index` 两位补零，同一来源多段时递增
- **保留原始扩展名**，不转码

## 六、C · 数量与来源多样性要求

| 要求 | 标准 | 理由 |
|---|---|---|
| 每类条数 | **3–5 段**（A6/B4 为可选补充，可到 5–8） | 少于 3 段无法区分"偶发"与"系统性" |
| 来源多样性 | 同类至少来自 **2 个不同设备/场景** | 单台设备的音色特征可能恰好不触发，造成假安全 |
| 单段时长 | 10–30 s | 见 2.1 |
| 总规模 | A 组 **18–30** 段 + B 组 **12–20** 段 = **30–50 段** | 若 A6/B4 扩到上限，总量约 56 段 |
| 单段大小 | 48 kHz/16-bit 单声道约 2.8 MB/30s | 总量约 90–150 MB，注意传输方式 |

### 6.1 录制技术规范（尽量遵守，做不到就在元数据里标注）

1. **优先 48 kHz / 16-bit 或 24-bit**，与现有 12 个文件一致（现有全部为 48 kHz 或 44.1 kHz / 16-bit）
2. **关闭手机上的"降噪""AI 增强""人声增强"** —— 这些会改变频谱，让结果无法代表真实部署
3. **关闭自动增益（AGC）**，否则无法记录真实音量
4. **不要用剪辑软件导出**，不要正规化（normalize）、不要压缩、不要降噪、不要淡入淡出
5. **距离**：优先按"实际部署位置"录（如床头柜、客厅茶几）；若做不到，统一录 1 m 和 3 m 两个距离
6. 条件允许时，**同一段声音用同一设备录"安静背景"作为对照**（10 s 空房间），用于判断底噪水平

### 6.2 优先级（如果只能先给一部分）

按"最可能造成严重后果"排序，建议先给前 4 类：

| 优先级 | 分组 | 理由 |
|---|---|---|
| ★★★ | A5 洗衣机结束提示音 | 多声电子蜂鸣，与报警器最像，几乎每天出现；**且无专属类兜底** |
| ★★★ | A1 手机闹钟 | 脉冲提示音，第四阶段已知 `Alarm` 类易被激活 |
| ★★★ | B2 宠物叫声（尤其猫） | 与婴儿哭声最像，且是长期存在的声源 |
| ★★★ | A3 电视声音 | 内容不可控，可能直接含报警音效 |
| ★★ | A2 微波炉、A4 吸尘器 | 常见但音色差异较明显 |
| ★★ | B4 婴儿笑声、成人哭 | 语义边界模糊，直接决定可用性 |
| ★ | A6 其他电子音、B1 谈话、B3 电视人声 | 兜底与补充 |

### 7.1 字段定义

## 八、E · 正样本 / 负样本 / 未知样本的划分

### 8.1 判定规则

| 类别 | 定义 | 本阶段用途 |
|---|---|---|
| **正样本** | **真正的烟雾报警器鸣叫**、**真正的婴儿哭声**（真实婴儿、真实设备） | 衡量检出能力（已有 3 段，可选补） |
| **负样本** | 日常声音，以及**容易被模型混淆的非目标声音** | 衡量误触发（本阶段主体） |
| **未知样本** | 无法确认真实类别（来源不明、听不清、内容混杂无法判定） | **单独存放，不参与任何统计**，只做定性查看 |

### 8.2 关键的第三条边界：语义正确但非真实危险（C 组）

这是本计划里最容易被忽略、但对产品最要命的一类：

> 电视里正在播放火灾新闻，背景有报警器音效。模型听到报警器声音 → 正确给出高分 → 系统触发提醒。

从**声学**上看这不是误报（模型确实听到了报警器）；从**产品**上看这是误报（家里没着火）。

两者必须分开统计，否则永远是笔糊涂账。所以单列 `C_semantic`：

| 子类 | 例子 | 统计归属 |
|---|---|---|
| `C1` 媒体中的报警声 | 电视/电影/短视频里的火警音效 | 单列，**不计入 A 组误报** |
| `C2` 媒体中的婴儿哭声 | 电视里的婴儿哭 | 单列，**不计入 B 组误报** |

这类样本的真正价值不是"证明会误报"（几乎必然），而是**量化它有多频繁、持续多久**，为后续"提醒降级"或"多模态复核"提供依据。

### 9.3 每段音频必须记录的字段

| 字段 | 说明 |
|---|---|
| `file` | 相对路径 |
| `label` / `group` | negative / positive / unknown，及 A1…C2 / existing |
| `frames` | 总帧数 |
| `inference_ms` | 推理耗时 |
| **`triggered`** | 该规则是否触发（是/否） |
| **`first_trigger_s`** | **首次触发时刻**（秒，窗尾） |
| **`trigger_episodes`** | 触发段数（中间可容忍掉帧，按 gap ≤ 1 帧合并） |
| **`trigger_duration_s`** | 首次触发段的持续时长 |
| **`trigger_frames_pct`** | 触发帧数 / 总帧数 |
| **`peak_stat`** | 该规则判定量的**峰值**（即使未触发也记） |
| **`margin_to_rule`** | 峰值 − 阈值（正=触发，负=差多少） |
| `top3_at_trigger` | 触发那一帧的 Top-3 类别与分数（用于归因：是被哪个类带起来的） |
| `energy_stats` | 峰值 dBFS、RMS、有声活动占比 |

**`peak_stat` 和 `margin_to_rule` 是最重要的两个字段。** 只记"是否触发"会浪费掉大部分信息：一个负样本峰值 0.44 而阈值 0.45，和峰值 0.05，是完全不同的两件事 —— 前者说明当前阈值就在悬崖边上，后者说明安全。这个信息只有记录峰值才拿得到。

| `reports/negative_eval_report.md` | 分组汇总结论 + 触发清单 + 边界样本（margin 最小的 5 个） |

### 9.5 报告口径（硬性约束）

**禁止表述：**

- ❌ "准确率 96%"
- ❌ "误报率 2%"
- ❌ "置信度 0.85"
- ❌ "模型识别出了微波炉"

**允许表述：**

- ✅ "在 24 段 A 组负样本中，3 段使 `R-S1` 触发，分别在 2.4 s / 5.6 s / 11.2 s"
- ✅ "最高判定量为 0.44（洗衣机结束提示音），距阈值 0.45 仅差 0.01"
- ✅ "`Smoke detector` 在该文件的逐帧分数为 0.31–0.44"

**并且必须写进报告的一句话：**

> 本批样本量（30–50 段）只能用于发现**定性风险**，不能用于估计误报率。真实误报率需要按部署环境（房间、距离、背景噪声、使用时段）分层的大规模连续录音。

### 9.6 不得删除"不符合预期"的样本

如果某段负样本触发了，**它不能删**。它是本阶段最有价值的产出之一。

处理方式：

1. 保留原始文件，在 `notes` 里标注"触发 R-S1 @ 2.4s"
2. 在报告里单列"触发清单"，逐条给归因（是哪个类带起来的、持续多久、能量多高）
3. 如果确认是"录音本身有问题"（如误录成了别的声音、文件损坏），**也不能删** —— 移到 `unknown/` 并在 `notes` 记录原因，同时在报告里说明"因 X 原因改判为未知"

只有一种情况可以排除统计：文件无法解码（损坏）。届时记录在报告的"处理失败"一节，与原文件一并保留。
